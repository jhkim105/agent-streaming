# Real-time AI Researcher Agent - Requirements

이 문서는 실시간 AI 리서처 에이전트(Real-time AI Researcher Agent) POC 프로젝트의 기능적 및 비기능적 요구사항을 정의합니다.

관련 문서: [시스템 아키텍처](2.architecture.md) | [기술 명세서](3.spec.md) | [구현 계획서](4.plan.md)

---

## 1. 프로젝트 개요
사용자가 복잡한 분석이나 시장 조사 질문을 입력하면, 에이전트가 백그라운드에서 웹 브라우징 및 정보 종합을 수행하고, 사용자는 대기 시간 없이 실시간으로 에이전트의 상태 및 생성되는 리포트를 확인하는 시스템을 구축합니다.

이 POC는 **소켓/스트리밍 통신 성능이 뛰어난 앞단(Kotlin Agent Stream Server)**과 **AI 개발 생산성이 뛰어난 뒷단(Python Agent Worker)**을 결합하고, **메시지 브로커(Kafka)와 캐시(Redis)**를 통해 마이크로서비스 간 비동기 결합을 완벽하게 처리하며, **독립된 프론트엔드(FE) 웹 UI**를 통해 사용자 경험을 최적화하는 아키텍처의 동작을 증명합니다.

---

## 2. 사용자 시나리오
1. **서비스 접속 & SSE 연결**: 사용자가 독립된 React 웹 UI에 접속하면 코틀린 스트리밍 서버와 SSE(`GET /api/chat/stream`) 커넥션이 자동으로 수립되고, 첫 이벤트로 유니크한 `Session ID`를 전달받습니다.
2. **질문 제출**: 사용자가 채팅 UI를 통해 리서치 질문을 등록합니다 (`POST /api/chat/message`, `Session ID` 포함). (예: *"최근 1주일간 발표된 생성형 AI 신기술 동향 요약 보고서 써줘"*)
3. **진행 로그 실시간 수신**: UI에 에이전트의 내부 작업 단계가 타임라인 형태로 실시간 로깅됩니다.
   * *예: [생각 중] ➔ [DuckDuckGo 검색 쿼리 추출] ➔ [검색 실행 중] ➔ [웹 페이지 본문 3건 요약 중]*
4. **리포트 타자기 효과 스트리밍**: 분석이 끝나면 에이전트가 완성해 나가는 보고서 마크다운 텍스트가 실시간 토큰 출력(타자기 효과)으로 렌더링됩니다.
5. **완료 및 에러 처리**: 리포트 생성이 완료되면 완료 신호(`DONE`)를 수신하고, 예외 발생 시 에러 메시지(`ERROR`)를 안전하게 수신 및 렌더링합니다.

## 3. 기능적 요구사항 (Functional Requirements)

### 3.1. 스트리밍 서버 및 클라이언트 소켓 제어 (Kotlin Agent Stream Server)
* **SSE 커넥션 및 세션 관리**: 클라이언트와의 1:1 Server-Sent Events 연결(`GET /api/chat/stream`)을 수립하고, 클라이언트별 `Session ID` 및 본인의 `Host ID`를 바인딩하여 기동 상태를 모니터링해야 합니다.
* **비동기 요청 처리**: 클라이언트로부터 수신한 질문(`POST /api/chat/message`)을 파이썬 에이전트에게 동기식으로 응답 대기하지 않고, `Session ID` 및 `Host ID`와 함께 카프카 토픽(`agent-requests`)에 즉시 발행하여 비동기 처리합니다.
* **실시간 중계**: 카프카 혹은 레디스로부터 수신한 토큰 청크 및 상태 이벤트를 해당하는 클라이언트의 SSE 채널로 올바르게 라우팅하여 중계해야 합니다.

### 3.2. AI 에이전트 워크플로우 (Python Agent Worker)
* **다단계 추론 엔진**: 사용자의 질문을 분석하고 웹 검색을 할 것인지, 수집된 페이지를 요약할 것인지 스스로 판단하여 단계를 밟아야 합니다 (LangGraph 적용).
* **도구 사용 (Tool Use)**:
  * **Web Search**: DuckDuckGo Search API(`duckduckgo-search`)를 통해 API Key 없이 최신 웹 정보를 조회합니다.
  * **Webpage Scraper**: 검색 결과의 URL들로부터 본문 콘텐츠를 가져와 텍스트(Markdown 형식 선호)로 파싱합니다.
* **실시간 이벤트 발행**:
  * 에이전트의 각 추론 단계(Thought, Tool Calling 등)를 로깅 이벤트(`type: STATUS`)로 발행해야 합니다.
  * 최종 리포트 생성 시, 토큰이 생성될 때마다 실시간으로 텍스트 조각(`type: CHUNK`)을 발행해야 합니다.
  * 예외 발생 시 에러 메시지(`type: ERROR`) 및 완료 시 완료 신호(`type: DONE`)를 발행합니다.

### 3.3. 분산 환경 라우팅 (Kotlin & Redis)
* **인스턴스 식별**: 각 코틀린 스트리밍 서버 인스턴스는 런타임에 본인의 유일한 식별자(UUID 기반 Host ID)를 보유해야 합니다.
* **메시지 라우팅**: 카프카에서 메시지를 수신한 코틀린 인스턴스가 해당 사용자의 세션을 쥐고 있지 않을 경우, 목적지 Host ID를 기반으로 Redis Pub/Sub 채널을 통해 올바른 코틀린 인스턴스로 이벤트를 라우팅해야 합니다.

### 3.4. 독립된 프론트엔드 웹 UI (Frontend - React)
* **독립 모듈 구동**: `Vite + React + TypeScript + Vanilla CSS` 기반 독립 SPA(Single Page Application) 웹 앱으로 개발되어 별도 포트(예: `:5173`)로 구동 가능해야 합니다.
* **실시간 타임라인 UI**: 에이전트의 현재 추론 상태(Search, Scrape, Summarize 등)를 스피너 또는 타임라인 카드로 시각화합니다.
* **마크다운 타자기 효과 렌더링**: 수신되는 마크다운 청크 텍스트를 실시간으로 파싱하고 타자기 효과로 연속 렌더링해야 합니다 (`react-markdown` 등 적용).
* **재연결 및 에러 UI**: SSE 연결 끊김 시 자동 재연결 로직 및 에러 발생 시 사용자 안내 토스트/Alert UI를 제공합니다.

## 4. 비기능적 요구사항 (Non-Functional Requirements)

### 4.1. 성능 및 지연시간 (Latency)
* **첫 단어 출력 시간 (TTFT)**: 사용자가 질문을 던진 후 첫 에이전트 진행 로그가 화면에 보이기까지의 대기 시간은 **1.5초 이내**여야 합니다.
* **스트리밍의 매끄러움**: Redis와 Kafka를 거치는 과정에서 토큰 병목이 발생해 화면상 스트리밍이 끊기거나 답답하게 출력되어서는 안 됩니다.

### 4.2. 확장성, 복원력 및 예외 처리 (Scalability, Resilience & Exception)
* **Scale-out**: 코틀린 스트리밍 서버를 여러 대 띄운 환경(다중 컨테이너)에서도 사용자 세션 매핑이 어긋나지 않고 완전히 보장되어야 합니다.
* **격리성 및 예외 전파**: 파이썬 에이전트 워커가 처리 지연이나 오작동(LLM Rate Limit, Web Scrape 실패 등)으로 예외를 발생시키더라도, 앞단 코틀린 스트리밍 서버 및 사용자 SSE 커넥션은 안전하게 에러 메시지(`type: ERROR`)를 수신하고 커넥션을 정리할 수 있어야 합니다.

### 4.3. 인프라 요구사항
* **컨테이너화**: 로컬 개발 및 테스트를 쉽게 시작할 수 있도록 Kafka, Redis 등의 미들웨어는 `docker-compose` 환경으로 원터치 실행이 가능해야 합니다.
